## Addendum: G1 fix PRD (authored 2026-09-05)

- **`dev/local/prds/backlog/00202-fix-merge-hlc-path-attribution-v1.md`** (standard template, 120 lines; `catchup: force`, `design: skip`, `default_model: opus`; citation checker clean).
- Root cause, verified by code reading + git history (bisect is the PRD's Phase 0): `check_commit_for_hlc` (`ddb-core/src/git_ops/read.rs:104-146`) diffs each commit against `parent(0)` only, so a merge commit counts as "touching" every file that arrived from its second parent and the HLC walk stops there. Since `c33b0a7` (00166, 2026-07-18) merge commits carry an HLC trailer, so on node B the file merged in from A is attributed the merge's HLC (> B's own 2000) and A wins; before `c33b0a7` the trailer-less merge yielded `None` and the id fallback picked B by accident. The Nightly log confirms: `left: "20260601000000"`, `right: "20260601000010"` at `sync_test.rs:310`. The same helper feeds `lww_pick` (`sync_manager/mod.rs:615-616`), so the fix also protects last-writer-wins after a prior merge.
- Fix: a merge commit "touches" a path only when its blob differs from EVERY parent's blob (transport-only merges become transparent to the walk); single-parent commits keep today's rule; the existing failing sync test is the pin, plus two helper-level tests (merged-in file → side commit's HLC; merge that rewrites a path → merge's HLC).
