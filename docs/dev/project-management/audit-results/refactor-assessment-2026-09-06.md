### F3 - The Tier-1 gate is heavy, rarely run in the loop, and blind to sync (L3, L4; self-verified; wording corrected by the panel)

- `cargo test-ci`: 42 CLI (1.6 s) + 1,555 core (952.8 s) + 222 server (0.6 s). The 565-test e2e crate (one process per test) runs its measured subsets in 16-34 s. CI `test.yml` on `c8b72bd` took 21 m 41 s end to end.
- Mechanism (confirmed): `parser::generate_unique_id` holds a process-global mutex across a 100 ms sleep until the wall second changes, with `exists()` inside the lock; `unique_ids` reserves future seconds so a following mint can spin ~N s. The core lib test binary is one process; static lower bound ~500 s from at least 498 mint-triggering test sites (267 `INSERT INTO` in `sql_engine/tests.rs` alone). Share of the 952 s is unmeasured; one timed run with the sleep stubbed under `cfg(test)` settles it (00164's SM1/SM2 tests depend on the reserved window and must be adapted). The held 00201 (UTC + sub-second + node suffix) removes the throttle for good.
- In practice the loop does not pay it per task: the only autopilot session log on disk (`last-session.log`, 00171) shows 1 `cargo test-ci` among 81 `cargo test` invocations; local-gate timings exist only for the three attended 00171 tasks. So the gate is a Definition-of-Done-as-practiced gap (what did the skipped gate let through?) more than a time driver.
- `test-ci` excludes `sync_test` (`.cargo/config.toml:2-4`); `test.yml` has run `sync_test` on every push since 2026-03-13, but pushes happened on 6 days in 7 weeks (SSH agent locked on the unattended host), so the 00166 regression `c33b0a7` sat unpushed 19 days inside the 26-day idle loop, then Nightly was red 30 days (08-07 to 09-05; 18 earlier "successes" were 6-20 s guard no-ops). Fixed attended as 00202 (5 commits, +471/-104).
- Local clippy 1.97.1 vs CI pin 1.89.0: two red pushes on 09-05.
- The lib "unit" tests are integration tests by the repo's own rule (`clean-architecture.md:76`); at most ~1,020 of 1,555 build a real repo; mocks live in one 574-line file.

Implication: fix the push credential first (it is the actual detection gap), add `--test sync_test` and the affected e2e modules to the per-task gate for git_ops/sync PRDs, measure the mint share once, and record how often Tier 1 actually runs per loop task.

- Latent hazards found by reading, unexecuted, each P0-class under the repo's "silent data loss" rule: (i) service update has no unique pre-check and materializes with `INSERT OR REPLACE` under a `UNIQUE` index, so updating a unique column to another row's value likely lands in git and evicts the sibling from the typed table (`update.rs:74-111`, `materialize.rs:923-928`, `ddl.rs:414-420`); (ii) `ddb delete` uses the reverse-only junction cleanup (`indexer/mod.rs:480`) while SQL DELETE uses the two-direction one (`dml.rs:1266`), so owner-side junction rows survive a CLI/GraphQL/REST/FFI delete; (iii) SQL DELETE runs no ON DELETE CASCADE walk (`dml.rs:681-712`, `:727` call only `check_restrict_blocks_delete`; `collect_cascade_children` is called only from `service/delete.rs:49`) while the docs imply CASCADE under the DELETE section; (iv, suspected) FFI raw create with content carrying an existing id overwrites it; (v, suspected) the read-outside-lock / commit-inside-lock shape at ~20 sites means two concurrent single-row updates to one doogat are whole-file last-writer-wins with no OID check (00195 scopes only 5 batch sites).

### F9 - NEW: server transaction scope is process-global (panel, architecture lens; judge upheld; self-verified)

- `DoogatService.txn: Option<TransactionBuffer>` lives on the service (`service/mod.rs:50-57`); the server actor owns exactly one `DoogatService` for every client (`actor/mod.rs:664-677`). `service::execute_sql` resumes the buffer into a fresh `SqlEngine` and suspends it back after every call, and skips `ensure_fresh` while it is set (`service/sql.rs:11-24`). PgWire routes every non-SELECT statement, BEGIN/COMMIT/ROLLBACK included, to `actor.execute_sql` (`pgwire.rs:102-114`); GraphQL `executeSql` does the same (`operations.rs:262`). Nothing in `ddb-server/src` resets `txn` on connection drop.
- Consequences (by reading, unexecuted): a PgWire client's BEGIN leaves the shared service in a transaction every other client inherits; a GraphQL `executeSql` INSERT from another connection is buffered into that transaction and reported as success without reaching git (`dml.rs:377-397`); a contract create on a singleton type runs inside the foreign SAVEPOINT (`with_immediate_transaction` returns `f()` directly when not autocommit, `indexer/mod.rs:686-692`) and its index rows are rolled back on that client's ROLLBACK while its git commit stays; a dropped mid-transaction PgWire connection wedges the SQL write path server-wide until restart.
- `docs/src/technical/server.md:51` documents the opposite ("BEGIN/COMMIT/ROLLBACK cannot span multiple GraphQL calls"). The only BEGIN e2e is a single-call CLI `ddb query "BEGIN; ...; COMMIT"` (`sql_lifecycle.rs:523,549`); no test drives BEGIN across calls on any server transport. The 09-05 backlog review saw the mechanism (N04) and filed it as a 00180 documentation task.
- 00172's closure actor keeps the single `&mut DoogatService`; 00196 as written makes the shared write plan buffer-aware, which extends the leak from SQL DML to contract create/update/delete.

Implication: a fifth design decision, made before 00196 and 00180: per-connection session handle owning the `TransactionBuffer`, or reject BEGIN on shared actor paths and keep `executeBatch` as the only atomic unit. Pre-flight gains a regression test and the doc correction.
