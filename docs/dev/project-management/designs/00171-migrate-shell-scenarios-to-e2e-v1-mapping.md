## Conventions

- One row per shell section, keyed by `file:line`. `smoke.sh` and `smoke.ps1`
  each get their own row per section (dialect pairs are never merged into one
  row), but where the two dialects are exact mirrors of one scenario they
  share ONE target Rust test — the `smoke.ps1` row says "dialect pair, same
  target as smoke.sh:LINE" instead of repeating the analysis.
- `needs server?` is `No` for every smoke row: neither `smoke.sh` nor
  `smoke.ps1` ever invokes `ddb serve` — both are CLI-only scripts (verified:
  no `serve` token appears in either file). All targets are `DdbTestRepo`
  (`repo.ddb()`), not `ServerGuard`.
- `must-fail?` is `Yes` when the section's body contains at least one
  expected-failure assertion (bash bare `!` / `|| true` + error-text grep,
  PowerShell `ddb-fails` / explicit `$LASTEXITCODE` check), even if the
  section is otherwise a success-path scenario.
- `status` is `TODO` for sections whose implementation or validation is pending.
  Sections
  fully satisfied by an existing test are marked `DONE (pre-existing, no port
  needed)` — the mapping table's job for those rows is to record the
  cross-reference, not to queue a Phase 1 task. (ASSUMPTION: the design doc's
  "updated to DONE per section as Phase 1 tasks land" describes ports; rows
  that need no port are marked DONE now rather than sitting as TODO forever.)
- `smoke.ps1` has zero CI coverage today (absent from `test.yml` and
  `full-validation.yml` — confirmed by the PRD/design's own grep). Its rows
  are still mapped in full per the 100%-coverage metric; this fact is noted
  once here rather than repeated in every `smoke.ps1` row.
